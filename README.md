# ПромПул (Artel)

B2B-платформа технологического матчинга и промышленной кооперации для AgTech и FoodTech:
заказчики публикуют потребность в замене импортных узлов, деталей и ингредиентов, отмечают её
«звёздами» с объёмом закупки, а российские производители объединяются в кооперации, чтобы её
закрыть.

Сейчас в репозитории технический фундамент (приложение, база данных, линтер, тесты, CI),
стартовая страница поиска и поиск по каталогу производителей с API, через которое производитель
будет заносить свои позиции. Регистрация, личные кабинеты, запросы и коллаборации будут
добавляться поверх.

## Быстрый старт

Нужен только Node.js 22+. Docker не обязателен: локальную PostgreSQL запускает сам Prisma
(`prisma dev`, база хранится в папке пользователя и переживает перезапуск).

```bash
cp .env.example .env     # переменные окружения
npm install              # зависимости (+ генерация Prisma Client)
npm run db:start         # локальная PostgreSQL в фоне (порты 51213–51215)
npm run db:deploy        # применить миграции
npm run db:seed          # демо-данные: «Деталь» от «ООО Обнал»
npm run dev              # http://localhost:3000
```

Поиск: введите «деталь» на главной или откройте <http://localhost:3000/search?q=деталь>.
Проверка, что приложение видит базу: <http://localhost:3000/api/health> должен вернуть
`{"status":"ok","db":"ok"}`.

После перезагрузки компьютера достаточно снова выполнить `npm run db:start` и `npm run dev`.
Остановить базу: `npm run db:stop`.

### Windows

Команды те же, их можно выполнять в Git Bash. В PowerShell или cmd вместо `cp` используйте
`copy .env.example .env`. Если порт 51214 занят, поменяйте порты в скрипте `db:start` в
`package.json` и в `.env`.

### PostgreSQL в Docker (необязательно)

Если Docker установлен, можно использовать его вместо `db:start`: в `.env` раскомментируйте
строку `DATABASE_URL` для Docker (и закомментируйте две строки выше), затем `npm run db:up`.
Запустить всё целиком в Docker (приложение + БД):

```bash
docker compose --profile app up --build
```

### Куда добавлять новый код

По мере роста платформы предметные области стоит выделять в отдельные модули внутри
`src/server/<модуль>/` (данные и бизнес-правила) и соответствующие маршруты в `src/app/`.
Ожидаемые модули по концепции продукта:

- `auth`, `users`: регистрация, вход, роли;
- `organizations`: профили заказчиков и производителей, верификация («Анти-Перекуп»);
- `requests`: технологические запросы (Issues) и «звёзды» спроса;
- `catalog`: каталоги продукции и мощностей производителей;
- `collaborations`: производственные кооперации и консорциумы.

Тесты кладутся рядом с кодом: `файл.test.ts`.

## Каталог и поиск

### Данные

- **`Organization`** — производитель: название, необязательные ИНН и город. Позже к ней
  привяжутся пользователи, и права на каталог будут идти через членство в организации.
- **`Product`** — позиция каталога, принадлежит организации: название, описание, цена в рублях
  (`Decimal`, с копейками), **срок производства в днях** (`leadTimeDays`), город производства и
  статус `DRAFT` → `PUBLISHED` → `ARCHIVED`. Покупатель видит не срок, а дату готовности: день
  просмотра (по Москве) плюс `leadTimeDays`. Поиск показывает только `PUBLISHED`.

Позиции читаются и пишутся только через `src/server/catalog/products.ts`: там проверка данных
(Zod-схемы в `schemas.ts`), принадлежность позиции организации и пересчёт поля `searchText`.
Страница поиска, API и сид пользуются одними и теми же функциями.

**Поиск** сейчас простой: запрос приводится к нижнему регистру (ё → е), у слов отбрасываются
частые окончания («детали» → «детал»), и позиция находится, если все слова есть в её
`searchText` (название, описание, город, производитель). Когда каталог вырастет, внутри
`searchProducts` его можно заменить на полнотекстовый поиск PostgreSQL или внешний движок,
не трогая страницы и API.

### API производителя

Основа для будущего режима производителя: интерфейс ввода позиций будет вызывать эти
эндпоинты. Входа в аккаунт пока нет, поэтому запись защищена общим ключом из
`SELLER_API_TOKEN` (заголовок `Authorization: Bearer <ключ>`); без переменной API выключено.
Когда появится авторизация, `checkSellerAccess` в `src/server/seller-access.ts` заменяется
проверкой сессии и членства пользователя в организации из адреса, маршруты не меняются.

| Метод и адрес                                      | Что делает                                   |
| -------------------------------------------------- | -------------------------------------------- |
| `GET /api/products/search?q=…`                     | Поиск покупателя (без ключа)                 |
| `POST /api/organizations`                          | Создать производителя                        |
| `GET`/`PATCH /api/organizations/{id}`              | Профиль производителя                        |
| `GET /api/organizations/{id}/products`             | Все позиции производителя, включая черновики |
| `POST /api/organizations/{id}/products`            | Добавить позицию (по умолчанию черновик)     |
| `GET`/`PATCH /api/organizations/{id}/products/{p}` | Позиция; правка полей, публикация, архив     |

Пример:

```bash
T=local-dev-seller-token-change-me   # значение SELLER_API_TOKEN из .env
ORG=$(curl -s -X POST localhost:3000/api/organizations -H "Authorization: Bearer $T" \
  -d '{"name":"ООО Пример","city":"Тула"}' | jq -r .id)
curl -s -X POST localhost:3000/api/organizations/$ORG/products -H "Authorization: Bearer $T" \
  -d '{"name":"Насос шестерённый","price":"25000.50","leadTimeDays":14,"city":"Тула","status":"PUBLISHED"}'
```

Поля позиции: `name`, `description`, `price` (число или строка, до 2 знаков после точки),
`leadTimeDays` (целое число дней, неделя = 7), `city`, `status`. Ошибки проверки возвращаются
с кодом 400 и описанием по полям, чужая или несуществующая позиция — 404.

## Переменные окружения

| ------------------ | -------------------------------------------------------------- |
